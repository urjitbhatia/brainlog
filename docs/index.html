brainlog

Transparent process wrapper that captures stdout, stderr, and stdin — with an MCP server so LLM agents can read your terminal output.

Install View on GitHub
Install

Get started in seconds

Grab the prebuilt binary, or build from source with Cargo.

Prebuilt binary
curl -fsSL https://raw.githubusercontent.com/urjitbhatia/brainlog/master/install.sh | sh

macOS & Linux, no Rust toolchain required. Linux builds are statically linked (musl).

From source
cargo install --git https://github.com/urjitbhatia/brainlog

Compiles from source — requires a Rust toolchain.

Features

Everything you need

Drop brainlog in front of any command and gain full observability with zero configuration.

Invisible Wrapping

PTY proxy so wrapped processes behave identically. Colors, interactive prompts, TUI apps — isatty() returns true, everything just works.

Full I/O Capture

Every byte of stdout, stderr, and stdin recorded with nanosecond timestamps in a compact framed binary format. Nothing is lost.

MCP Server for Agents

7 tools let LLM agents discover, read, search, and watch process output directly — no copy-pasting required.

Auto-restart & Resume

Keep services alive with --restart, and resume named services across sessions. Long-running processes made easy.

Killer Feature

Your agent waits for
exactly the right moment

Instead of sleeping blindly and hoping a server is up, wait_for_pattern blocks until a regex appears in the process output — then returns immediately. Like Playwright's waitForText, but for any terminal process.

No polling loops. No arbitrary timeouts. No racing against a server that isn't ready yet. The agent proceeds with certainty.

configurable timeout regex pattern returns matched line works on running processes

Quick Start

Wrap any command

Prefix any command with brainlog — the process runs exactly as before.

terminal
# Wrap any process — transparent to the child
$ brainlog node server.js
$ brainlog python app.py
$ brainlog cargo build
 
# Name your services for easy reference
$ brainlog -n my-api node server.js
$ brainlog -n worker -t env:prod ./run.sh
 
# Auto-restart on exit
$ brainlog run --restart -- node server.js
 
# Resume a previous service (same name, new run)
$ brainlog run --resume my-api -- node server.js
 
# Start the MCP server for Claude Code / other agents
$ brainlog mcp
Agent Setup

Connect to your agent

Brainlog speaks MCP — add it to any agent that supports the protocol.

One command — globally available across all projects:

terminal
$ claude mcp add brainlog -- brainlog mcp
 
# Or scope to a single project
$ claude mcp add --scope project brainlog -- brainlog mcp

Add to codex.json or your project config:

codex.json
{
  "mcpServers": {
    "brainlog": {
      "command": "brainlog",
      "args": ["mcp"]
    }
  }
}

Add to .cursor/mcp.json in your project root:

.cursor/mcp.json
{
  "mcpServers": {
    "brainlog": {
      "command": "brainlog",
      "args": ["mcp"]
    }
  }
}

Standard MCP server config — works with any MCP-compatible agent:

mcp config
{
  "brainlog": {
    "command": "brainlog",
    "args": ["mcp"],
    "transport": "stdio"
  }
}
CLI

Full command-line interface

View logs, search output, control processes, and manage storage — all from the terminal.

View Logs

# List tracked services (newest first)
brainlog list
# Group by executable + working directory
brainlog list -g
 
# View logs by name, service ID, or run ID
brainlog logs my-api
# Last 50 lines
brainlog logs my-api --tail 50
# Follow (like tail -f)
brainlog logs my-api -f
# Stderr only
brainlog logs my-api -s stderr

Search

# Regex across all services
brainlog search "ERROR|WARN"
 
# Scoped to one service
brainlog search "panic" --service my-api

Process Control

# Send SIGTERM (graceful stop)
brainlog kill my-api
# Force kill (SIGKILL)
brainlog kill my-api -f
# Send a specific signal
brainlog kill my-api -s HUP
 
# Restart via wrapper (SIGUSR1)
brainlog restart my-api

Housekeeping

# Delete services older than 7 days
brainlog purge --before 7d
 
# Preview what would be purged
brainlog purge --before 1h --name tmp --dry-run
MCP Server

7 tools for LLM agents

A complete toolkit for agents to observe, query, and control your processes without any manual copy-pasting.

Tool Description
list_recent_runs Last N runs across all services, newest first — best for "what just happened?"
discover_services Find tracked services by name, cwd, tags, port, executable, status, or exit code
get_logs Read stdout, stderr, or stdin by service ID, run ID, or working directory
search_logs Regex search across all services with timestamps and context lines
wait_for_pattern Block until a regex appears in output — like Playwright's waitForText
kill_service Send a signal (SIGTERM, SIGKILL, etc.) to stop a running process
restart_service Restart a running process via its wrapper (SIGUSR1)
Agent Workflow

Agents know what's happening

A natural sequence of tool calls gives any LLM agent full situational awareness over your running processes.

1
list_recent_runs
"What just ran?" — See the last N runs with status, exit codes, and optional log previews.
2
discover_services
"What's running in this project?" — Filter by cwd to scope to the current repository.
3
get_logs
Read output by ID or by cwd shorthand — no need to discover first.
4
search_logs
Find errors, warnings, or specific patterns across all tracked commands with regex.
5
wait_for_pattern
Start a server, then wait for "listening on port 3000" before proceeding.
Internals

How it works

Built on solid Unix primitives — PTY, SQLite, and a compact binary frame format.

PTY Proxy

Allocates a pseudo-terminal so the wrapped process behaves identically. isatty() returns true, colors and interactive prompts work, and terminal dimensions are inherited.

Framed Binary Logs

Every byte of stdout, stderr, and stdin is recorded with nanosecond timestamps. Frame format: [timestamp_ns:u64][stream:u8][len:u32][payload]

Auto-naming

Services without -n get a derived name from working directory and executable. LLM enrichment can generate human-readable names from initial output.

SQLite + WAL

Service and run metadata lives in a SQLite database with WAL mode for concurrent reads. Logs are compact binary files in ~/.brainlog/logs/.

Storage layout

~/.brainlog/ brainlog.db # SQLite (WAL mode) — service + run metadata config.yaml # optional LLM enrichment config logs/<run-id>/ stdout.log, stderr.log, stdin.log # per-stream framed binary logs combined.log # interleaved stream
