Good, I've read all three files. The picture is getting clear. I have a few remaining questions before I can write the
  implementation plan:

  A. LLM Integration

  - For both the auto-enrichment at startup (generating name/description from command context) and the semantic service
  matching in the MCP server — which LLM provider? Anthropic API? OpenAI? Should it be configurable? 
  
  Answer: Configurable, BYOK (bring your own key) for all providers. Support multiple providers
  through a unified OpenAI-compatible HTTP client, since Ollama, OpenRouter, OpenAI, and Gemini all
  speak the same /v1/chat/completions protocol. For Anthropic, use CLI invocation (claude -p)
  rather than implementing their bespoke API format — keeps the Rust codebase to a single HTTP
  client path. Also support CLI-based invocation for other providers (e.g., ollama run) as a
  fallback/alternative to HTTP calls.

  Supported providers:
  - Ollama (local, no key needed, base_url: localhost:11434/v1)
  - OpenRouter (BYOK or OpenRouter key, base_url: openrouter.ai/api/v1, access to 200+ models)
  - OpenAI (direct, base_url: api.openai.com/v1)
  - Gemini (Google AI key, base_url: generativelanguage.googleapis.com/v1beta/openai)
  - Anthropic (via claude -p CLI invocation, no HTTP client needed)
  - Any OpenAI-compatible provider (user sets custom base_url)

  Config example (~/.brainlog/config.yaml):
    llm:
      provider: ollama
      model: llama3.2:3b
      api_key: null
      # base_url: null          # override for custom providers

  Enrichment is optional — if no provider/key is configured, brainlog still works as a pure
  capture tool without LLM features.

  Where does the API key come from (~/.brainlog/config, env var, both)?

  Answer: Both. Resolution order: 1) config.yaml llm.api_key, 2) env var per provider
  (ANTHROPIC_API_KEY, OPENAI_API_KEY, OPENROUTER_API_KEY, GEMINI_API_KEY), 3) None (fine for
  Ollama and Anthropic CLI mode).

  - What model tier for these calls? They're relatively simple classification/extraction tasks — a small/fast model (Haiku,
   GPT-4o-mini) would suffice and keep costs negligible.
   Answer: Yes, simpler models are fine.

  C. Storage Layout

  - One global SQLite database at ~/.brainlog/brainlog.db, or per-project databases? Global seems simpler and enables

  Answer: Yes, global is fine. 
  
  - For raw byte streams: separate files per stream (stdout.log, stderr.log, stdin.log) or a single interleaved file with

  D. Log Stream Format

  - Since you want raw byte streams preserved AND time-range filtering AND unified view — I'm leaning toward a framed
  binary format: each chunk stored as [timestamp][stream_type][length][raw_bytes]. This gives us interleaving for unified
  view, per-stream filtering, and time-range queries all from one file. The SQLite would store metadata + index offsets.
  Sound right?

  answer: yes
